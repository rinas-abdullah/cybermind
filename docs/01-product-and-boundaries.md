# المرحلة 1 — نطاق المنتج والحدود

> **حالة الوثيقة:** مسودة تشغيلية — يُحدَّث عند كل قرار رئيسي.  
> **الغرض:** توحيد فهم المؤسسة قبل توسيع البنية التحتية أو التصميم.

---

## 1. الرؤية المختصرة

**Risaq** منصة تدريب وتمكين في **الأمن السيبراني** تجمع بين:

- مسارات تعلم وتدريب عملي (سيناريوهات، طرفية، تقدم).
- طبقة تحليلات ومؤشرات (متعلم، مؤسسة، امتثال تقريبي).
- دعم ذكاء اصطناعي مساعد (إرشاد، تحليل، رؤى) ضمن حدود واضحة.

---

## 2. الشخصيات (Personas)

| المعرف | الوصف | احتياجات رئيسية |
|--------|--------|------------------|
| `learner` | متعلم / متدرب | تسجيل، متابعة تقدم، تدريب، لوحة شخصية، لوحة صدارة |
| `instructor` | مدرب / مشرف تعليمي | رؤية تقدم المجموعة، تحليلات (حسب الصلاحيات) |
| `admin` | مسؤول منصة / مؤسسة | لوحة إدارة، تقارير مؤسسية، إدارة مستخدمين (بحث/تقارير) |
| `visitor` | زائر غير مسجّل | صفحات عامة، تسجيل/دخول، معاينة مسارات |

**ملاحظة تنفيذية:** الأدوار في الكود الحالي تُمثَّل عبر `userRole` ووسائط `requireRole` في الـ API — يجب أن تبقى خريطة الشخصيات متوافقة مع هذه الأدوار.

---

## 3. وحدات المنتج (Modules) — مطابقة للوضع الحالي

كل وحدة = نطاق وظيفي يمكن تطويره، اختباره، وتوثيقه بمعزل نسبي.

| الوحدة | الوصف | نقاط دخول تقريبية في المشروع |
|--------|--------|--------------------------------|
| **Identity & Access** | تسجيل، دخول، جلسة، JWT، صلاحيات | `/auth`, `/api/auth/*`, `auth.js` |
| **Learning Surface** | مسارات تعلم، صفحات عامة | `/learn`, `learn.html` |
| **Practice & Training** | مهام، تدريب، سيناريوهات | `/practice`, `/training` |
| **Terminal Lab** | محاكاة طرفية | `/terminal` |
| **Progress & Gamification** | نقاط، مستويات، لوحة صدارة | `/leaderboard`, `/api/*` ذات الصلة |
| **Dashboard (Learner)** | لوحة المتعلم، مخططات، مرشد AI | `/dashboard`, `app.js` |
| **Analytics & Insights** | تحليلات، رؤى AI، ملف متعلم | `/analytics`, `/ai-insights`, `/learner-profile` |
| **Scenario Intelligence** | تحليل سيناريو | `/analyze-scenario` |
| **Admin / Institution** | تقارير مؤسسية، امتثال، بحث مستخدم | `/admin`, `adminDashboard.js` |
| **i18n** | عربي/إنجليزي، RTL | `translations.js`, `i18n.js` |
| **Build & Deploy** | حزمة إنتاج | `build.js`, `dist/` |

**حدود الوحدة:** كل وحدة يجب أن تعرف واجهاتها (API أو أحداث واجهة) دون الاعتماد على تفاصيل داخلية لوحدات أخرى قدر الإمكان (هدف تدريجي، ليس شرطاً ليوم واحد).

## 4. خارج النطاق — الإصدار الأول (v1) — يُراجع دورياً

ما يلي **لا يُفترض** أنه مضمون أو مطلوب في v1 ما لم يُدرج صراحةً لاحقاً:

- [ ] دفع إلكتروني / اشتراكات فوترة كاملة  
- [ ] تطبيق جوال أصلي (Native)  
- [ ] امتثال قانوني معتمد (ISO/SOC2) كشهادة جاهزة — يمكن «الاستعداد» تقنياً دون ادعاء الاعتماد  
- [ ] تعدد مستأجرين كامل (multi-tenant) مع عزل بيانات صارم — حسب التصميم الحالي قد يكون تدريجياً  

*(ضع علامة ✅ عند اعتماد أي بند للنطاق.)*

## 6. استراتيجية المستودع (Repository)

**القرار الحالي (مسجّل):** مستودع **أحادي** (monorepo) يضم:

- `backend/` — خادم Express و API  
- `frontend/` — صفحات HTML  
- `js/`, `css/` — أصول الواجهة المشتركة  
- `build.js` — حزمة `dist/` للنشر  

**الأسباب (ملخّص):** تبسيط الإصدارات، مراجعة واحدة، ونشر متسق للواجهة والخادم في مرحلة النمو.

**متى إعادة النظر:** إذا انفصل فريق كامل على خدمة مستقلة مع دورة إصدار مختلفة → راجع `docs/decisions/` وأضف ADR جديداً.

---

## 7. معايير قبول لإغلاق «المرحلة 1»

تُعتبر المرحلة 1 مكتملة عندما:

1. وافق ممثل المنتج + التقنية على هذا المستند (أو نسخته المحدَّثة).  
2. جدول NFR في القسم 5 **مُعبَّأ** أو مُعلَّم صراحةً بـ «غير مطلوب في v1».  
3. قائمة «خارج النطاق» مرئية للجميع ولا تُضاف ميزات كبيرة دون تحديث الوثيقة.

---

## 8. الخطوة التالية (معاينة المرحلة 2)

بعد إغلاق المرحلة 1:

- تثبيت **بيئات** (dev / staging / prod) ومتغيراتها.  
- **أسرار** خارج المستودع + سياسة تدوير.  
- **CI** (بناء + اختبارات تزداد تدريجياً).  
- نسخ احتياطي واسترجاع **مُختبَر** لقاعدة البيانات عند الاعتماد على PostgreSQL.
